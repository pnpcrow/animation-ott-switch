# 로컬 저장·백업·향후 Drive 동기화

## 현재 구현

`ott-switch-library` IndexedDB의 `bookmarks`, `categories`, `settings`, `meta` 저장소를 사용한다. 쓰기는 전체 상태를 하나의 read-write 트랜잭션에서 읽고 검증한 뒤 반영한다. 별도 보관함 탭이나 재시작된 서비스 워커에서도 트랜잭션이 직렬화되어 변경을 잃지 않는다. 기기 ID와 마지막 수정 시각은 영속 메타데이터다.

같은 ID는 `updatedAt`이 최신인 레코드가 이긴다. 동시각이면 삭제 기록이 우선하고, 기기 ID와 정렬된 직렬화 값으로 결정을 고정한다. 병합은 방향에 무관하고 같은 백업을 여러 번 병합해도 동일하다. 가져온 시각보다 다음 로컬 수정 시각을 크게 만들어, 기기 시계가 잠깐 뒤로 돌아가도 사용자의 새 수정이 우선한다. 레코드 단위 병합이므로 같은 작품의 서로 다른 필드를 동시에 수정하면 한쪽 레코드가 선택된다. 필드별 병합은 향후 개선이다.

삭제는 실제 제거 대신 `deletedAt`을 기록한다. 카테고리를 삭제해도 작품은 남고, 삭제된 카테고리 ID는 화면과 그룹 내보내기에서 무시한다. 오래된 백업이 삭제한 그룹이나 작품을 되살리지 못한다. 작품 페이지에서 사용자가 명시적으로 다시 저장하면 해당 북마크를 복구한다.

플랫폼 공식 작품 ID가 같은 저장은 중복을 만들지 않는다. 다른 플랫폼끼리 제목만 같은 경우에는 동명 작품 오병합을 막기 위해 자동 합치지 않는다. 독립적으로 저장한 동일 플랫폼 작품을 가져오면 로컬 ID로 매핑한다. 여러 기존 작품을 하나로 이어 붙이는 충돌은 자동 병합하지 않고 파일 전체를 거부한다. 미래의 다중 기기 동기화에서는 이 로컬 ID 매핑을 영속 별칭/redirect 레코드로 확장해야 한다.

## 파일 형식

최대 10MB JSON, 작품 20,000개, 카테고리 1,000개다. 파일의 버전·타입·필드 길이·ID 중복·시각·HTTPS 이미지 URL·허용된 OTT 상세 URL을 전체 검사하고 오류 시 아무것도 쓰지 않는다. 검증은 알려진 필드만 복사하므로 임의 필드와 객체 프로토타입이 DB에 들어가지 않는다.

전체 백업은 설정, 개인 메모, 즐겨찾기, 삭제 기록까지 포함한다. 그룹 내보내기는 선택한 살아 있는 카테고리와 소속 작품만 포함한다. 다른 카테고리 소속, 구독 설정, 메모와 즐겨찾기는 공유 파일에서 제외한다. 그룹 가져오기는 기존 개인 메모·즐겨찾기·설정과 다른 카테고리 소속을 보존하며, 로컬에서 삭제한 작품을 공유 파일 때문에 복구하지 않는다. 사용자가 지정한 이미지 URL·소개는 공유 대상이다.

이미지 바이트는 저장하거나 내보내지 않으며 브라우저의 HTTP 캐시를 사용한다. 캐시는 서버의 Cache-Control과 브라우저 상황에 따라 재검증될 수 있다.

## Google Drive 선택 기능의 설계

아직 Google 계정에 접속하거나 파일을 업로드하지 않는다. 이후 고정 확장 ID, Chrome 확장용 OAuth 클라이언트, 동의 화면이 준비되면 `drive.appdata` 범위로 전용 JSON을 저장한다. 앱 전용 폴더는 앱만 접근하며 사용자의 일반 Drive 파일 권한이 필요하지 않다.

동기화 순서는 로컬 스냅샷 읽기 → 원격 파일과 버전 읽기 → 검증 → 삭제 기록을 포함한 병합 → 버전을 조건으로 원격 쓰기 → 성공한 결과를 로컬에 다시 병합이다. 원격이 바뀌면 다시 읽고 제한된 횟수만 재시도한다. 오프라인 변경은 로컬에서 계속 가능하다. 최초 파일 생성 경쟁, 재인증, 대용량 분할, 기기별 확인 시점과 tombstone 보존 기간, 중복 작품 ID 별칭, 시계 오차를 해결한 다음 실제 연결을 제공한다. 삭제 기록은 모든 기기가 확인하기 전 임의 정리하지 않는다.

참고: [Drive 앱 데이터 폴더](https://developers.google.com/workspace/drive/api/guides/appdata), [IndexedDB 트랜잭션](https://developer.mozilla.org/en-US/docs/Web/API/IDBTransaction).
