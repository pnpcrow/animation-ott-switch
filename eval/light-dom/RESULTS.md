# 경량 DOM 모델 실측 결과

2026-11-13 평가에서는 **DOM 특징을 학습한 6.5 KB 선형 모델이 다음 적용 검토 후보로 가장 유망했습니다.** 새로운 4작품의 제목·대표 이미지·작품 소개 12개를 모두 골랐고, 전체 정답은 기존 일반 규칙 11/18에서 14/18로 늘었습니다. 표본은 작고 비작품 화면 오인이 남으므로 확장 프로그램에 기본 탑재하거나 자동 이동 판단을 맡기지는 않았습니다.

조사한 공개 소형 모델 가운데 한국어 reranker, 다국어 NLI, 35 MB 영어 tiny reranker를 실제 양자화 가중치로 실행했습니다. 이 입력 구성에서는 실제 작품 요소 선택 성과가 낮았고, 다운로드 크기가 작아도 브라우저 메모리와 지연이 컸습니다. 아래 수치는 해당 checkpoint·q8 형식·입력·실행 설정에 대한 관측이며 모델의 모든 활용 가능성에 대한 결론이 아닙니다.

## 조사와 평가 범위

MarkupLM·NewsXLM DOM-LM·HTML-T5처럼 DOM/HTML을 직접 다루는 모델도 확인했습니다. 공개된 과제와 한국어 지원, 이미지 선택 범위, 실제 가중치 크기, 준비된 브라우저 실행 경로가 이번 조건에 맞는지 검토했습니다. 일반 pretrained model에 무작위 분류 head를 붙여 실패한 실험처럼 보고하지 않았습니다. 상세한 배포본·라이선스·원문은 [조사 문서](RESEARCH.md)에 있습니다.

공개 모델 세 개는 DOM 전용 학습 모델이 아니며 후보별 NLI/관련도 점수를 이용한 전이 실험입니다. 구조 모델은 사람이 정의한 일반 DOM/문자열 형태 특징에 이번 과제의 가중치를 학습한 **새로운 태스크 전용 프로토타입**입니다. 서로 동일한 학습 이력을 가진 범용 모델의 순위표로 해석하면 안 됩니다.

이미 결과를 본 66개 문제는 전부 개발용입니다. 소형 신경망의 영문/한국어 역할 template와 단일 threshold, 구조 모델의 특징·정규화·계수를 모두 고정한 뒤 새로운 6페이지를 검증했습니다. 4개 작품 페이지와 장르·약관 페이지 2개이며, 각 페이지에서 3필드를 채점합니다. 18문제가 18개의 독립 웹페이지는 아닙니다. 세부 수집 방법과 정답 근거는 [DATASET.md](DATASET.md)에 있습니다.

## 새 자료에서의 정확도

| 조건 | 전체 18개 | 비자명한 17개 | 실제 작품 필드 / 12 | 필드 없음 / 6 | 잘못된 실제 후보 선택 |
| --- | ---: | ---: | ---: | ---: | ---: |
| DOM 구조 선형 모델, native/Chrome JS | **14** | **13** | **12** | 2 | 4 |
| 기존 일반 DOM 규칙 | 11 | 10 | 10 | 1 | 7 |
| MiniLM NLI, native/WebGPU | 7 | 6 | 1 | 6 | 1 |
| Jina tiny, native/WebGPU/WASM | 6 | 5 | 0 | 6 | 0 |
| KURE nano, native/WebGPU | 5 | 4 | 2 | 3 | 4 |
| 항상 `none`으로 답하는 기준 | 6 | 5 | 0 | 6 | 0 |

한 이미지 문제는 실제 관측 후보가 없어 추론 없이 `none`이 정답입니다. 이를 숨기지 않고 전체 18개와 해당 문제를 뺀 17개를 모두 보고합니다. Jina의 오선택 0은 좋은 추출 능력이 아니라 **모든 실제 작품 필드도 보류한 결과**입니다. 세 신경망의 신규 자료에 대한 native/browser 추론은 예정된 비어 있지 않은 17개 문제·128개 후보를 완료했습니다.

구조 모델은 기존 규칙이 맞힌 11개를 유지하고 3개를 추가로 맞혔습니다. 그러나 장르 페이지의 제목·이미지와 약관 페이지의 제목·소개를 작품 요소로 잘못 선택했습니다. 따라서 **작품 화면 판정과 후보 선택을 구분**해야 합니다. 적용 검토 위치는 기존 상세화면 판정 내부의 후보 점수화 단계입니다. 이 결과만으로 검색 결과의 동일 작품 검증이나 자동 이동을 허용할 수는 없습니다.

NLI는 native와 브라우저에서 전체 점수는 같지만, 이미지·소개 두 문제의 정오가 서로 뒤바뀌었습니다. 단순히 전체 정답 수가 같다고 수치 동등성을 주장하지 않습니다. 실제 브라우저 logits에 개발 때 고정한 threshold를 적용해 따로 채점했습니다. KURE와 Jina도 native/browser 출력 오차를 기록했습니다.

## 실제 실행 비용

가중치 크기와 RSS는 decimal MB, 시간은 관측한 한 필드의 후보 묶음 처리 시간입니다. 다운로드와 브라우저 프로세스 시작 시간은 아래 추론 시간에 포함되지 않습니다.

| 실행 조건 | 모델/토크나이저 준비 파일 | 신규 필드 추론 중앙값 | 격리 Chrome 전체 RSS 시작 → 관측값 |
| --- | ---: | ---: | ---: |
| DOM 구조 모델, Chrome JS | 모델 JSON **6,540 B** + JS 특징/추론 코드 | 반복 측정 약 **1.0 ms** | 전체 프로세스 RSS는 측정하지 않음 |
| MiniLM NLI q8, WebGPU 요청 | **124.50 MB** | 첫 실행 **1.41초** | **409 → 1,484 MB** |
| Jina tiny q8, WebGPU 요청 | **35.46 MB** | 첫 실행 **0.80초** | **411 → 1,116 MB** |
| Jina tiny q8, WASM | **35.46 MB** | 첫 실행 **0.89초** | **408 → 643 MB** |
| KURE nano q8, WebGPU 요청 | ONNX **151.09 MB**, tokenizer/설정 등 포함 약 **152.48 MB** | 첫 실행 **10.56초** | **411 → 최대 1,351 MB** |

표의 준비 파일 크기는 ONNX Runtime 배포 파일을 제외합니다. 실제 신경망 실행에는 별도 JS/WASM 런타임 자산도 필요합니다. KURE는 실제로 embedding Gather까지 int8로 양자화해 200 MB 가중치 탐색 기준을 충족했지만, 이 노트북의 브라우저 구성에서는 가볍게 실행되지 않았습니다.

구조 모델 시간은 관측 객체의 feature pack·특징·벡터 생성, 점수화, 선택을 모두 포함합니다. 30회×10호출의 묶음 반복 중앙값이며 최초 실행도 별도 저장했습니다. 실행 소스 hash 기록을 보강해 같은 코드를 재실행했을 때 최초 측정 약1.2 ms, 최종 측정 약1.0 ms였고 **18개 선택은 모두 같았습니다**. 후보를 역순으로 넣어도 같은 ID를 18/18 유지했습니다. 실제 사이트 DOM 수집·이미지 다운로드·렌더링은 이 시간에 포함되지 않습니다. JS heap만으로 전체 RAM 사용량을 주장하지 않습니다.

신경망 브라우저 측정은 Python에서 미리 토큰화한 tensor를 사용해 tokenizer의 시간과 메모리가 제외됩니다. 반대로 구조 모델의 측정에는 관측 특징 전처리가 포함됩니다. 따라서 이를 전체 확장 기능의 지연 비율이나 CPU/GPU 성능 순위로 환산하지 않습니다.

개발 6문제에서 반복 측정한 warm 중앙값은 NLI WebGPU 약885 ms, Jina WebGPU 약623 ms, Jina WASM 약828 ms였습니다. KURE WASM 6문제×3회에서는 약11.22초였으며 GPU 요청 경로도 큰 개선을 보이지 않았습니다. Jina의 WASM 메모리 증가량은 약235 MB로 WebGPU의 약705 MB보다 낮았습니다. 이 추가 WASM 비교는 실행 비용 확인용이며, 정확도가 잘 나온 provider로 설정을 다시 고른 것이 아닙니다.

브라우저는 ONNX Runtime Web 1.31.1, WASM 1 thread입니다. GPU queue 제출을 실제 관측했지만 지원되지 않는 연산은 CPU와 섞여 실행됩니다. 순수 GPU 실행으로 표현하지 않습니다. 한 대의 개발 노트북에서 작업이 병행됐고, 특히 추가 Jina WASM 측정은 KURE 실행과 CPU 자원을 공유했습니다. native CPU는 모델별 thread 수도 다릅니다. 저사양 기기나 실제 extension offscreen worker의 성능 보장은 아닙니다.

RSS는 해당 격리 Chromium 프로세스 집합의 관측 작업 집합입니다. JS heap, private commit, GPU 논리 버퍼 크기, 누적 GPU 할당량과 같지 않습니다. 공유 GPU 메모리는 RSS와 겹칠 수 있어 더하지 않습니다. 브라우저 시작 메모리와 모델 로드 후 증가량을 분리해야 하며, 정확한 단일 모델 물리 RAM으로 간주하지 않습니다.

## 구조 모델의 학습과 한계

174개 특징 계수는 태그·부모·가시성·메타데이터·이미지 크기·문자열 형태 등에서 학습했습니다. 서비스별 CSS나 작품명 사전을 입력하지 않지만, 특징 설계 자체는 사람이 했습니다. 기본 언어 모델처럼 새 의미를 자유롭게 추론하거나 변경된 모든 사이트를 자동 이해하지 않습니다.

개발 자료의 작품/페이지 그룹 14개를 묶어 5-fold로 정규화 강도를 선택했습니다. 최선 교차검증은 51/66, 전 개발 자료를 학습한 후 그 자료에 대한 점수는 65/66입니다. 전자는 설정 선택용 개발 수치, 후자는 재학습 자료 점수이며, 위의 신규14/18과 구분합니다. 신규 표본도 4개 서비스의 익숙한 레이아웃이므로 새로운 서비스·개편된 DOM으로의 일반화는 입증되지 않았습니다.

현재 구현은 실험 도구와 학습된 모델 파일까지입니다. 확장 프로그램의 추출·검색·북마크·스위치 기본 동작은 변경하지 않았습니다. 실제 적용 전에는 비작품 화면 거절, 로그인/모달/재생 전환, 새로운 레이아웃, 검색 결과 항목의 작품 동일성 판정을 별도 자료로 검증해야 합니다. 이번 신규 결과를 활용해 수정한다면 이 18개도 개발 자료로 돌려야 합니다.

## 재현과 독립 검증

[통합 채점 JSON](reports/comparison.json)은 고정 입력·선택·모델과 원본 실행 계획 해시를 검사하고 native/browser를 따로 채점합니다. [독립 재채점](reports/independent-audit.json)은 기존 채점 함수를 호출하지 않고 원시 logits와 허용 정답 ID로 다시 계산했습니다. 두 결과의 수치가 일치합니다.

실제 모델 가중치·tokenizer·runtime revision과 파일 hash, 후보 단위 logits, 실행 계획, 브라우저 자원 기록을 보존했습니다. 대용량 공개 모델 가중치와 HTML/스크린샷 원본은 Git에 넣지 않습니다. 직접 학습한 6,540 B 모델은 저장소에 포함합니다. [README](README.md)의 재현 절차와 모델별 문서를 참고하세요.

Node 계약 테스트 34개와 Python 계약 테스트 8개가 통과했습니다. 실제 browser 추론·동적 ONNX 입력 수치 검사·독립 재채점·고정 파일의 저장소 바이트 일치도 확인했습니다. 평가 도구만 바꾸었으므로 확장 프로그램 전체 E2E는 이번 작업에서 다시 실행하지 않았습니다.
